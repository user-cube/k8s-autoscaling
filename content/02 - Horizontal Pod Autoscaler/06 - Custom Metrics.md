# 06 - Custom Metrics

CPU and memory are sufficient for many workloads, but they are not always the best indicators of application demand.

A web application that spends most of its time waiting for database queries may have low CPU utilization even while receiving thousands of requests per second. A message consumer might process thousands of events while barely using any CPU.

In these situations, scaling based solely on resource metrics becomes ineffective. To solve this, Kubernetes supports **Custom Metrics** — allowing the HPA to scale applications using metrics exposed by the application itself.

---

## What Are Custom Metrics?

A custom metric is any metric generated by an application running **inside the Kubernetes cluster**. Unlike CPU and memory, these values are not collected automatically by the Metrics Server — they are exposed by the application and translated into a format Kubernetes can understand.

Typical examples:
- HTTP requests per second
- Active user sessions
- Request latency
- Active WebSocket connections
- Cache hit ratio
- Database connection pool usage
- Business-specific metrics

The HPA treats these metrics exactly like CPU or memory once they are available through the Kubernetes API.

---

## Why Use Custom Metrics?

Infrastructure metrics measure resource consumption. Custom metrics measure **application behavior**. These two are not always related.

```
Current CPU: 22%
→ Looks idle

Current requests/s: 4,800
→ Under heavy load
```

The API spends most of its time waiting for external services — CPU stays low, but user traffic has increased dramatically. Scaling on CPU would not create additional Pods. Scaling on requests per second would.

## Architecture

```mermaid

Application --> Prometheus --> PrometheusAdapter[Prometheus Adapter] --> KubernetesAPI[Kubernetes API] --> HPA --> Deployment
```

Unlike native resource metrics, Kubernetes cannot understand application metrics directly. A translation layer is required.

---

## The Complete Workflow

### 1. Application Exposes Metrics

The application publishes metrics using a monitoring library:

```
http_requests_total
http_request_duration_seconds
active_sessions
shopping_cart_requests
```

Common instrumentation libraries:

| Framework | Library |
|---|---|
| Spring Boot | Micrometer |
| Go | Prometheus Client |
| .NET | prometheus-net |
| Python | Prometheus Python Client |
| Node.js | prom-client |

### 2. Prometheus Collects Metrics

Prometheus periodically scrapes the application's `/metrics` endpoint and stores every metric in its time-series database. Unlike the Metrics Server, historical data is preserved.

### 3. Prometheus Adapter

The HPA cannot query Prometheus directly. The **Prometheus Adapter** bridges the gap:

- Queries Prometheus
- Converts Prometheus metrics into Kubernetes format
- Exposes the `custom.metrics.k8s.io` API

```
Prometheus → Prometheus Adapter → custom.metrics.k8s.io
```

### 4. Kubernetes API

The adapter registers the `custom.metrics.k8s.io` API group. From the HPA's perspective, there is no difference between a custom metric and a native CPU metric — everything looks like a Kubernetes-native metric.

### 5. Horizontal Pod Autoscaler

The HPA retrieves the custom metric and applies the same control loop logic:

```
HTTP Requests observed: 820 req/s
Target:                 500 req/s
→ Scale up
```

---

## Example

Every Pod should handle approximately **250 requests per second**:

```yaml
metrics:
  - type: Pods
    pods:
      metric:
        name: http_requests_per_second
      target:
        type: AverageValue
        averageValue: "250"
```

Current workload:

| Pod | Requests/s |
|---|---|
| frontend-1 | 280 |
| frontend-2 | 305 |
| frontend-3 | 260 |
| **Average** | **281** |

281 > 250 → HPA increases replica count.

---

## Types of Custom Metrics

**Pod Metrics** — each Pod exposes its own metric; the HPA computes the average across all replicas:

```
frontend-1 → requests/s = 310
frontend-2 → requests/s = 285
Average    → 297.5 req/s
```

**Object Metrics** — the metric belongs to another Kubernetes object rather than individual Pods, useful when workload is better represented by a shared resource:

```
Ingress → requests per second → HPA
```

## Advantages

| Benefit | Description |
|---|---|
| Better Representation | Metrics describe actual application behavior, not infrastructure usage |
| More Accurate Scaling | Scaling decisions align directly with user demand |
| Business-Oriented | Scale on meaningful indicators — orders, active customers, API transactions |
| Reduced Over-Provisioning | Scale only when business activity increases, not when CPU happens to spike |

---

## Challenges

Custom metrics introduce additional operational complexity. If any component in the chain becomes unavailable, scaling may stop:

```
Application → Prometheus → Adapter → HPA
```

Applications must also expose high-quality metrics. Poorly designed or rapidly fluctuating metrics lead to unstable scaling behavior. Choosing the correct metric is often more important than choosing the correct threshold.

---

## Best Practices

> [!tip]
> Select metrics that represent actual workload demand rather than infrastructure utilization.

> [!tip]
> Keep metric names stable and descriptive — they appear in HPA configuration and dashboards.

> [!tip]
> Validate custom metrics in Prometheus before connecting them to the HPA.

> [!warning]
> Avoid metrics that fluctuate rapidly — they can cause excessive and oscillating scaling activity.

> [!note]
> The Metrics Server does **not** expose custom metrics. A Metrics Adapter is always required.

---

## Key Takeaways

- Custom metrics allow scaling based on application-specific behavior rather than infrastructure usage
- Metrics originate from workloads running **inside** the Kubernetes cluster
- Prometheus collects these metrics; the Prometheus Adapter translates them into `custom.metrics.k8s.io`
- The HPA consumes custom metrics exactly as it consumes CPU or memory
- Well-designed metrics produce significantly better scaling decisions than infrastructure metrics alone
